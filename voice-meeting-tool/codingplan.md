# 语音处理工具 · 编码计划（给 AI 的完整任务书）

> 用法：把本文件的**全部内容**复制粘贴给 AI，或告诉 AI「读取 `voice-meeting-tool/codingplan.md` 并严格按它执行」。
> AI 无需也不应索取任何 API Key——密钥一律从本地 `.env` 读取，由**你本人事后填写**。

---

## 一、任务目标

开发一个**本地运行的语音处理命令行工具**，输入一个（或多个）音频文件（录音、会议录音、语音邮件等），输出**整理好的会议纪要 / 备忘 / 结构化内容**（Markdown 文件）。

处理链路：
```
录音文件(mp3/m4a/wav/...)
   → ① 语音转文字（语音识别 / ASR）
   → ② 文字清洗与分段
   → ③ 用 LLM 整理成结构化会议纪要（议题 / 结论 / 待办 / 人物发言）
   → ④ 输出 Markdown 文件
```

## 二、硬性要求：API Key 如何处理（最重要）

⚠️ **这条优先级最高，必须严格遵守：**

1. **AI 不得要求用户提供任何 API Key**。AI 需要 key 时，只需让代码从环境变量或 `.env` 读取，变量值用占位符表示。
2. 代码中**禁止硬编码任何真实密钥**，只允许出现 `os.environ["XXX_API_KEY"]` 这类读取方式。
3. 项目提供 `.env.example`（变量名 + 空值/占位符说明），并附带说明文档，告诉用户「把 `.env.example` 复制成 `.env`，填上自己的 key」。
4. `.gitignore` 中必须包含 `.env`（确保密钥不进 git）。
5. **AI 的最终交付里，必须明确列出用户需要自己填写的所有环境变量**，每个都标注用途（例如：`VISION_API_KEY`=语音识别服务的 key，`LLM_API_KEY`=整理纪要的大模型 key）。

## 三、实现语言与技术选型（由 AI 决定，但据此考虑）

- 首选 **Python 3.10+**：语音生态最成熟（faster-whisper / openai-whisper / librosa / pydub 等）。
- 音频解码：`pydub` + ffmpeg（需在交付说明里写清 ffmpeg 安装方式）。
- 语音转文字（ASR）：优先考虑**无需自建模型**的方案，例如调 API（OpenAI / Gemini / 其他兼容端点）；若走本地，可考虑 faster-whisper，但要写明资源/依赖成本。
- 纪要整理 LLM：通过 OpenAI 兼容 API 调用。**协议与地址来自环境变量**，让用户可自由填自己的 baseUrl / model / key（例如本机 Ollama、或任意 OpenAI 兼容网关）。
- 依赖用 `requirements.txt` 或 `pyproject.toml` 管理。

## 四、CLI 设计（供参考，可优化）

```
python voice_tool.py <音频文件...> [--out DIR] [--lang zh]
  --lang   指定识别语言（默认自动检测）
  --out    输出目录（默认 ./out）
  --config 指定 .env 路径（默认读取当前目录 .env）
```

## 五、交付物清单

1. 完整可运行的源码（含入口脚本）。
2. `requirements.txt`（或 pyproject.toml）+ 安装说明。
3. `.env.example`（占位变量）。
4. `README.md`：安装、ffmpeg 依赖、配置、用法、示例。
5. `.gitignore`（含 `.env`）。
6. **一个「你需要手动填写的环境变量」清单**,精确到变量名和用途。

## 六、验收标准

- 不向用户要 key，代码零硬编码密钥。
- 提供示例音频的假数据路径或合成一段测试音频的脚本（无版权问题）。
- 能端到端跑通：音频 → Markdown 纪要。
- 输出纪要包含：会议主题、时间、参与者发言要点、结论、待办（负责人/截止时间，若有）。
